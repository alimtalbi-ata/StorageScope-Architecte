# StorageScope V6.222 — Registre anti-rejeu SAN/NAS inter-snapshots

**Auteur : Abdelhalim Talbi** · 24 octobre 2026 · changement proposé (PR draft).

## Besoin et portée

Les versions V6.219–V6.221 vérifient les HMAC, les doublons dans un seul
snapshot et la rotation de clés. Elles ne reconnaissent pas une collecte signée
présentée de nouveau dans un snapshot ultérieur. V6.222 ajoute un **point
d'enregistrement explicite** utilisant un registre SQLite local persistant.

Ce mécanisme n'est pas appelé par la revue de risques en lecture seule :
`--storage-risk-file` et l'interface de diagnostic conservent leur sémantique
historique. La protection inter-snapshots est effective **uniquement** lorsque
l'opérateur emploie `--storage-replay-register` avec le même registre protégé.

## Protocole de collecte

1. Chaque observation SAN/NAS inclut `source_ref`, `observed_at` ISO 8601 avec
   fuseau, et `collection_id` (UUIDv4 canonique minuscule). `collection_id` est
   créé une seule fois pour chaque collecte d'une source. Les observations de
   la même source dans un snapshot partagent cet identifiant.
2. Le collecteur signe **tous ces champs** avec `sign_observation`, et conserve
   la politique `storagescope.observation-auth-policy.v2` et les clés HMAC dans
   l'environnement de l'opérateur, jamais dans le fichier JSON.
3. Le processus de contrôle vérifie toutes les signatures, la politique v2,
   les horodatages, les doublons intra-snapshot et les résultats des analyses
   risques/dépendances. Toute preuve incomplète est refusée **avant écriture**.
4. Une transaction SQLite `BEGIN IMMEDIATE` enregistre les couples
   `(source_ref, collection_id)` sous clé primaire unique. En cas de doublon,
   **toute la transaction est annulée**, y compris les autres sources du lot.
   Deux processus concurrents ne peuvent donc pas accepter le même ID.

## Commandes (exemples ; aucune exécution sur infrastructure réelle)

```powershell
# Initialisation explicite et non réinitialisable d'un registre local.
StorageScope.exe --storage-replay-init C:\StorageScopeData\replay.sqlite
# Accepter une collecte signée ; retourne un reçu JSON minimal sur stdout.
StorageScope.exe --storage-replay-register C:\Inventaires\signed.json C:\StorageScopeData\replay.sqlite
# Rejeu : code de sortie non nul, aucune ligne ajoutée au registre.
```

Le registre absent, altéré, non conforme ou remplacé par un lien symbolique est
refusé ; il n'est **jamais recréé automatiquement** lors d'un enregistrement.
L'initialisation échoue si un fichier existe déjà. La sauvegarde/restauration
et les ACL du registre relèvent de l'opérateur.

## Sécurité et limites

- Le HMAC est une preuve de possession d'un secret partagé, pas une identité
  indépendante de collecteur ni une attestation d'horloge.
- SQLite n'est pas un journal inviolable : une restauration ancienne, une
  suppression ou un remplacement autorisé du registre peut permettre un rejeu.
  Une ancre externe signée et une stratégie de sauvegarde/restauration sont à
  concevoir avant toute revendication de non-répudiation.
- Le contrôle de fraîcheur V6.216 reste distinct et doit être activé avec une
  politique de référence explicite ; le registre ne mesure pas la fraîcheur.
- Aucune découverte réseau, écriture CMDB, remédiation ou action sur baie.
- Les fichiers sources historiques sans `collection_id` restent analysables en
  lecture seule, mais **ne sont pas admissibles** dans ce registre.

## Qualification attendue

Tests unitaires : acceptation, rejeu inter-snapshots, altération, ID modifié,
politique rétrogradée, lot multi-sources atomique, concurrence, registre absent,
registre corrompu, symlink, CLI et non-régression lecture seule. Test Windows
natif : scénario complet sur `StorageScope.exe` compilé avec un registre
SQLite temporaire et des signatures synthétiques. La CI Windows et ses
artefacts doivent être examinés avant de déclarer la version qualifiée.

**Alignement** : ISO 27001/27040 (intégrité et traçabilité des preuves),
ISO 42010 (contrat explicite entre collecte et analyse), ITIL 4 (audit des
observations), TOGAF/ArchiMate (traçabilité des dépendances). Cet alignement
n'est pas une certification.

## Réparation du lanceur de tests historiques (même cycle)

La suite cumulative Linux locale révélait trois erreurs de **staging**, sans
lien avec le moteur de rejeu : le benchmark V6.59 n'était pas colocalisé avec
son test ; la déclaration de captures V5.63 manquait ; le workflow de mise à
jour V5.89 n'était présent que dans les archives. Le lanceur
`scripts/run_tests.py` restaure désormais explicitement ces trois fixtures,
refuse les collisions et réutilise le restaurateur historique existant.
Aucun test n'a été désactivé et aucun workflow archivé n'a été activé en CI.
Trois tests ciblés vérifient les anciens parcours. Le test synthétique qui
échoue volontairement à l'intérieur d'un test de propagation d'échec n'est
pas un échec de la suite principale.
