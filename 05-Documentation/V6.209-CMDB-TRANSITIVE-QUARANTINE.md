# StorageScope V6.209 — Quarantaine transitive des identités CMDB

**Auteur : Abdelhalim Talbi.** 24 octobre 2026. Statut : correctif proposé sur branche dédiée ; qualification Windows V6.209 à constater dans les workflows, non présumée.

## Problème réel reproduit

Avant correction, une observation A (serial=S1, WWN=W1) et B (serial=S1, WWN=W2) produisaient `QUARANTINE_IDENTITY_CONFLICT`, mais les relations A–C et C–D, fondées sur WWN=W1, restaient `REVIEW_REQUIRED`. L'interface pouvait donc exposer des relations « à revoir » sans avertissement de leur appartenance à un ensemble d'identités contradictoires. Cette ambiguïté pouvait induire une décision humaine fondée sur des preuves contaminées. Les tests synthétiques V6.209 reproduisent le défaut avant correctif.

## Contrat du correctif

1. Construire un graphe non orienté sur les **candidats partageant un identifiant fort normalisé** (serial, WWN, UUID). Aucun rapprochement sur nom seul ; provenance obligatoire.
2. Identifier les extrémités de toute arête portant une contradiction d'identité forte (`direct_conflict_indices`).
3. Propager la quarantaine à tous les sommets accessibles dans la même composante connexe (`propagated_quarantine_indices`), sans propagation vers les composantes indépendantes.
4. Conserver l'action `QUARANTINE_IDENTITY_CONFLICT` sur les contradictions directes ; changer `REVIEW_REQUIRED` en `QUARANTINE_LINKED_IDENTITY_CONFLICT` sur les relations contaminées. Les composantes saines restent `REVIEW_REQUIRED`.
5. Conserver les limites existantes : 10 000 enregistrements, 50 000 paires candidates, lecture JSON bornée à 8 MiB, refus des clés dupliquées, SHA-256 des octets lus, export exclusif sans écrasement, **zéro fusion automatique**.

Le parcours du graphe est O(V+E) hors tri local, avec V ≤ 10 000 et E ≤ 50 000. Les nouveaux champs sont additionnels au schéma `storagescope.reconciliation.v1` ; ils ne constituent pas une API d'écriture.

## Architecture et gouvernance

```text
Snapshot CMDB / inventaires constructeurs (lecture seule)
    -> validation JSON UTF-8 stricte et SHA-256 exact
    -> rapprochement des identifiants forts + provenance
    -> graphe des preuves et détection des contradictions
    -> propagation de quarantaine sur composantes connexes
    -> rapport de revue + Diagnostic Windows (aucune écriture CMDB)
```

Le changement soutient ISO/IEC/IEEE 42010 (justification des décisions d'architecture), TOGAF/ArchiMate (traçabilité des relations entre composants), ITIL 4 (qualité des éléments de configuration), ISO 27001 et ISO 27040 (intégrité et gestion prudente des informations d'infrastructure). **Aucune certification de conformité n'est revendiquée.** Une empreinte SHA-256 garantit une détection de modification, pas l'authenticité du fournisseur.

- Régressions existantes `test_inventory_reconcile_v619.py`, `test_inventory_reconcile_provenance_v6197.py`, `test_cmdb_review_desktop_v6198.py`, `test_cmdb_snapshot_digest_v6208.py`.
- CI gouvernance Linux/Windows avec **contrôle explicite du code retour** ; CI native Windows PyInstaller/Inno Setup avec test de l'exécutable gelé, installation, désinstallation, portable, manifestes SHA-256.
- Les captures réelles GUI et l'acceptation humaine sont **non réalisées** tant qu'aucune preuve vérifiable n'est produite. Les exemples de ce document sont synthétiques.

## Limitations

La quarantaine est conservatrice : un conflit dans une composante peut suspendre des observations pourtant correctes, jusqu'à arbitrage humain. Les sources peuvent contenir des identifiants obsolètes ou usurpés ; aucune identité n'est considérée authentifiée par le seul snapshot. `main` doit rester inchangée, sans fusion automatique.
