# StorageScope V6.202 — Frozen Windows vendor snapshot CLI

**Auteur : Abdelhalim Talbi**  
**État : PR draft ; qualification native Windows à constater sur l'exécution CI du commit exact.**

## Besoin et changement vérifiable

Le cycle V6.201 introduit la normalisation hors ligne des inventaires NetApp ONTAP, Dell PowerScale et Pure FlashBlade. Les tests de la bibliothèque et l'entrée de la page Diagnostic ne suffisent pas à prouver la présence du module dans le binaire PyInstaller. V6.202 expose donc un point d'entrée explicite dans `storagescope_windows.main()` :

```powershell
StorageScope.exe --vendor-snapshot-file C:\captures\snapshot.json C:\rapports\normalise.json
```

Le fichier de sortie doit être **absent** au démarrage. La normalisation ne contacte pas les équipements et ne modifie ni CMDB ni configuration SAN/NAS. Les données proviennent uniquement d'un JSON fourni par l'opérateur, avec `source_ref` et horodatage UTC.

## Contrat de qualification

1. L'import statique de `vendor_snapshot_import_v6201` doit être présent dans la fermeture des modules calculée par `windows_module_inventory.reachable_modules`, utilisée par le fichier `StorageScope.spec`. Un simple test d'import Python ne suffit pas à démontrer l'empaquetage.
2. Les tests ciblés doivent passer sous Linux et Windows : dispatch CLI, préservation de l'entrée, export non écrasant, rejet des propriétés JSON dupliquées et inclusion dans la fermeture PyInstaller.
3. La CI native doit **construire** l'exécutable PyInstaller et l'installateur Inno Setup, puis lancer le **binaire compilé** pour chacun des trois constructeurs avec des fixtures synthétiques explicitement identifiées. Chaque rapport doit conserver le constructeur, le schéma, la provenance, un système, un partage, `OBSERVED_ONLY` et `automatic_changes=0`.
4. Le binaire doit refuser la réutilisation d'un chemin de sortie sans altérer son SHA-256, puis refuser un JSON à clé dupliquée sans créer de rapport.
5. Les contrôles préexistants restent obligatoires : suite historique Windows, auto-test d'échec contrôlé, rejet SQLite corrompu, installation/désinstallation, portable, manifeste binaire et SHA-256. L'artefact ne peut être annoncé comme qualifié que si **toute** cette chaîne passe.
6. Le ZIP des sources doit être construit au commit de tête exact de la PR, avec hash SHA-256, sans substitution par le commit de merge GitHub.

## Chaîne et responsabilités

```text
Snapshot JSON fourni par l'opérateur (synthétique en CI)
  -> StorageScope.exe --vendor-snapshot-file
  -> parser strict (limites, doublons, NaN, provenance)
  -> mapping explicite NetApp / PowerScale / FlashBlade
  -> modèle canonique storagescope.storage-topology.v1
  -> rapport JSON exclusivement nouveau
  -> inspection humaine ; aucune écriture CMDB
```

La cartographie est un élément de la couche technologique ArchiMate ; aucun lien applicatif ou niveau de service n'est inféré. Les limites, la séparation des responsabilités et les preuves relèvent d'ISO/IEC/IEEE 42010 et TOGAF. Le contrôle humain de la CMDB suit l'esprit d'ITIL 4 ; la validation des données, la non-altération des preuves et l'absence de secrets relèvent d'ISO 27001/27040.

## Limites et preuves à ne pas inventer

Les exemples de snapshots utilisés dans les tests sont **synthétiques**, non des captures d'équipements. Les essais de binaire ne prouvent pas le fonctionnement des API propriétaires ni l'ergonomie de la page Diagnostic. Les captures réelles d'interface et les tests UX humains ne sont pas fournis. La version interne du produit reste 6.108 ; V6.202 identifie le cycle de développement. Les conclusions CI, les numéros de run, les hashes et les binaires ne doivent être renseignés qu'après exécution réelle et vérification.
