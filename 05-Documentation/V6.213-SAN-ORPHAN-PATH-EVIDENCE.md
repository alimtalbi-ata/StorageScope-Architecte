# StorageScope V6.213 — Unresolved SAN path evidence

**Author:** Abdelhalim Talbi. **Scope:** offline SAN dependency review; no discovery, network writes, CMDB updates or remediation.

## Business problem and correction

An orphan SAN path (unknown host, absent host ID, wrong endpoint kind, or unknown storage array) was correctly flagged by the risk assessor, but the dependency report did not expose its count or, where safe, the affected array. With a separate healthy path, the dependency table could appear entirely verified despite an unresolved observation.

The dependency report now contains `unresolved_path_observations` (global number of orphan/non-object path records), and each trusted storage array contains its own `unresolved_path_observations` count. An orphan is attributed to an array **only** when the target ID uniquely identifies a trusted storage array. The record never creates a host-array relationship. Unattributable records remain in the global count, without guessed endpoints. Any orphan makes dependency assessment `INCOMPLETE`; existing healthy observations remain visible but do not erase uncertainty.

Windows Diagnostic displays `Observations de chemins sans relation résolue` and `chemins_orphelins=N` for each storage asset. This is an observation count, not a count of affected hosts or application services.

## Architecture / governance

Read-only topology JSON → risk assessor (findings) → dependency mapper (trusted endpoints + orphan counts) → JSON report and desktop text projection. The change supports ISO/IEC/IEEE 42010 evidence traceability, ITIL 4 configuration/dependency management and ISO 27001/27040 risk review. It is not a complete application-service dependency map, not an automated CMDB reconciliation, and does not establish actual impact or redundancy.

## Evidence limits

Fixtures are synthetic. No real Windows GUI screenshots or manual UX validation are provided in this change. No SHA-256 or Windows qualification claims are made without corresponding build artefacts and logs.
